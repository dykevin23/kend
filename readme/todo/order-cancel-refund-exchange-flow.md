## 1. 세 가지 행위는 서로 다르다

지금까지 "취소"라는 말로 뭉뚱그려 썼지만, 실제로는 **시점·주체·처리단위·결제영향이 전부 다른 세 가지 행위**다.

| | **주문취소** | **환불신청(반품)** | **교환신청** |
|---|---|---|---|
| 시점 | 배송 시작 **전** | 배송완료 **후** | 배송완료 **후** |
| 누가 신청 | 구매자 또는 판매자 | 구매자 → 판매자 승인 | 구매자 → 판매자 승인 |
| 처리 단위 | `order`(판매자 단위) 또는 `order_group`(전체) | `delivery_item`(상품 단위, 부분 가능) | `delivery_item`(상품 단위) |
| 결제 영향 | Toss **전액**취소 | Toss **부분**취소 | 원칙적으로 없음 (차액 있으면 별도 정산) |
| 재고 영향 | 즉시 복원 | 판매자가 반품 수령 확인 후 복원 | 기존 상품 복원 + 신규 상품 재차감 |
| 새 배송 생성 | 없음 | 없음 | 있음 (교환품 발송) |
| DB 상태값 | `orders.status = cancelled` | `delivery_items.status = return_requested → returned` | `delivery_items.status = exchange_requested → exchanged` |

**핵심 포인트**: "주문취소"는 아직 물건이 안 나갔을 때 계약 자체를 무르는 것이고, "환불신청/교환신청"은 물건을 받은 뒤 처리하는 사후 조치다. 지금까지 우리가 만들고 테스트한 건 전부 **주문취소**뿐이고, 환불신청/교환신청은 **설계만 있고 코드가 전혀 없다.**

## 2. 데이터 모델 현황 — 이미 준비된 것 vs 안 만들어진 것

### 이미 설계·구현된 것
- `order_groups.status`: `payment_in_progress` · `payment_pending` · `paid` · `partially_refunded` · `refunded` · `cancelled` · `failed`
- `orders.status`: `pending` · `confirmed` · `preparing` · `shipped` · `delivered` · `cancelled`
- `deliveries.status`: `pending` · `preparing` · `shipped` · `in_transit` · `delivered`
- `delivery_items.status`: `normal` · `cancelled` · **`return_requested` · `returned` · `exchange_requested` · `exchanged`**

### 설계는 있는데 아무도 안 쓰는 것 (2026-07-27 코드 전수 확인 결과)
- `delivery_items.status`의 `return_requested`/`returned`/`exchange_requested`/`exchanged` 4개 값 — **schema.ts에 정의만 돼 있고, kend/kend-seller 전체 코드에서 참조하는 곳이 0건.** 즉 반품/교환을 처리할 그릇은 만들어놨는데 아직 아무 로직도 안 들어있는 상태.
- `order_groups.status`의 `refunded`/`partially_refunded`도 마찬가지로 정의만 있고 세팅하는 코드 없음.
- kend-seller엔 상품 등록 시 "반품지/반품배송비" 입력 필드(`product-return-card.tsx`)가 있지만, 이건 **상품에 붙는 정적 메타데이터**일 뿐 실제 반품 신청/승인 워크플로우가 아님.

### 아예 설계도 안 된 것
- "교환신청"은 로드맵(P2-9 "반품/환불 처리 UI")에 명시적으로 언급조차 없다 — 반품/환불만 항목으로 잡혀있고 교환은 누락. 이번에 새로 짚어야 할 항목.

## 3. 전체 라이프사이클 (주문→결제→배송→구매확정→사후처리)

```
[담기] → [결제하기] → payment_in_progress ──(실패/이탈)──► failed ─┐
              │                                                      │
              ▼ 성공                                                 │ (cron, 30분)
             paid ──(구매자 취소 or 판매자 취소)──► orders.cancelled │
              │         └─ order_group 내 전 주문 취소 시 그룹도 cancelled ─┘
              │              └─ 재고 자동복원 (트리거, 구현됨)
              ▼
     orders: pending → confirmed → preparing → shipped → delivered
                                                              │
                                          ┌───────────────────┼────────────────────┐
                                          ▼                   ▼                    ▼
                                     [구매확정]          [환불신청]            [교환신청]
                                    (P3-1, 미구현)   (delivery_item 단위,   (delivery_item 단위,
                                          │             미구현)                미구현)
                                          ▼
                                   이후 취소/환불/교환
                                   불가하게 잠가야 함
                                   (아직 잠금 로직 없음)
```

**지금 실제로 코드가 있는 구간은 `payment_in_progress` ~ `delivered`까지의 배송 흐름과, 그 사이에 끼어드는 "주문취소"뿐이다.** `delivered` 이후(구매확정/환불신청/교환신청)는 전부 앞으로 만들어야 할 영역.

## 4. 현재 구현 상태 총괄

| 행위 | kend (구매자 웹) | kend-seller (판매자 웹) |
|---|---|---|
| 주문취소 (배송 전, 그룹 전체) | ✅ `cancelOrderGroup` — Toss 전액취소 연동됨, 버튼 노출 로직 수정 완료 | ✅ `updateOrderStatus`(주문 단위 취소) — **단, Toss 환불 미연동 (🚨 버그 #3, 보류)** |
| 재고 복원 (취소 시) | ✅ DB 트리거로 양쪽 경로 다 커버 (2026-07-27 구현) | ✅ 상동 |
| 재고 차감 (주문 시) | ✅ `decrement_stock` (2026-07-24 구현) | 해당 없음 (주문 생성은 kend에서만 발생) |
| 품절/재고부족 표시 | 해당 없음 | ✅ 상품목록 뱃지 (2026-07-24 구현) |
| 구매확정 | ❌ 미구현 (버튼만 있고 동작 없음, `orders/pages/order-action.ts`에 intent 없음) | 해당 없음 |
| 환불신청(반품) | ❌ 미구현 (신청 UI 없음) | ❌ 미구현 (승인/거절 UI 없음, 반품 수령 확인 없음) |
| 교환신청 | ❌ 미구현 | ❌ 미구현 |
| 배송현황 조회 | ❌ 미구현 ("배송조회" 버튼이 동작 없는 껍데기, `order-group-card.tsx`) | ✅ 스마트택배 연동(P2-3) 완료 — kend만 못 보여주고 있음 |

## 5. 알려진 미해결 이슈

1. **🚨 (버그 #3) kend-seller 주문취소가 Toss 결제취소를 호출하지 않음** — 판매자가 취소해도 고객 돈이 안 돌아감. kend가 Toss 시크릿을 갖고 있으므로 kend 쪽에서 트리거/Edge Function으로 자동화 필요. **부분환불(판매자별 금액)이라 전액환불보다 리스크 높음 — 별도 설계 필요.**
2. **구매확정 이후 잠금 로직 없음** — 구매확정 개념 자체가 아직 없어서, 배송완료된 주문도 이론상 계속 취소 가능한 상태로 남아있을 수 있음 (`canCancel`이 `delivered`를 이미 막고 있어 현재는 실질 위험 낮음).
3. **로드맵에 "교환" 항목 자체가 없음** — P2-9는 "반품/환불"만 명시, 교환은 별도로 추가해야 스코프에 잡힘.

## 6. 개발 단계별 테스트 매트릭스

### 현재 (P2-4 재고차감/복원 — 완료)
- [x] 단일 판매자·단일 상품 → 판매자 취소 → 재고복원 + 그룹승격 (실앱 검증 완료)
- [x] 단일 판매자·멀티 상품(한 주문) → 전체취소 → 전 상품 재고복원 (실앱 검증 완료)
- [x] 구매자 취소(cancelOrderGroup) → 재고복원 (실앱 검증 완료)
- [ ] 다중 판매자 주문 중 1곳만 취소 → 그룹 유지 / 나머지 취소 시 그룹 승격 (DB 시뮬레이션만, 실앱 미검증)
- [ ] 재고부족 시 체크아웃 에러 UX (실제 사용자에게 뭐라고 뜨는지)
- [ ] 동시성 (재고 1개, 동시주문 2건)
- [ ] `expire_pending_orders` cron 자연 발생(30분 방치) 확인

### #3 환불 자동화 구현 시 (미착수)
- [ ] 판매자 취소 → Toss 부분취소 실제 호출 → 고객 결제수단에 환불 반영 확인
- [ ] 부분취소 후 `payments`/`order_groups` 금액·상태 정합성
- [ ] 환불 API 실패 시 재시도/알림 (pg_net 비동기 실패 케이스)

### 구매확정(P3-1) 구현 시 (미착수)
- [ ] 수동 구매확정 버튼 동작
- [ ] 배송완료 후 N일 자동 구매확정 (cron)
- [ ] 구매확정 후 취소/환불신청 차단되는지 (`canCancel`, 환불신청 진입 조건에 가드 추가 필요)

### 환불신청/교환신청(P2-9 확장, 미착수 — 로드맵에 "교환" 항목 추가 필요)
- [ ] delivery_item 단위 환불신청 → 판매자 승인/거절
- [ ] 승인 후 반품 수령 확인 → 해당 수량만 재고복원 (현재 트리거는 order 전체 단위라 item 단위로 재설계 필요)
- [ ] 승인 후 Toss 부분환불
- [ ] 교환신청 → 기존 delivery_item `exchanged` 처리 + 신규 delivery/delivery_items 생성 + 재고 반영(기존 복원 + 신규 차감)
- [ ] 한 주문 안에서 일부는 환불, 일부는 교환이 동시에 진행되는 케이스

## 7. 정책 결정 필요 항목 (개발 착수 전 팀 결정 필요)

이 섹션은 코드로 확인 가능한 "현재 상태"가 아니라, **비즈니스 판단이 필요한 미결정 사항**이다.
답을 여기 미리 채우지 않은 이유는 기술 문제가 아니라 정책 문제라서다 — 결정되는 대로 이 문서를 갱신한다.

### 7.1 주문취소
- [ ] 취소 가능 마지노선을 정확히 어느 상태로 볼 것인가 — 지금 코드는 `shipped`/`delivered` 전(즉 `preparing`까지는 허용)인데, "판매자가 주문확인(`confirmed`)한 뒤에는 취소 불가"처럼 더 이른 시점에서 막을지
- [ ] 판매자가 취소할 때 **사유 입력을 필수로 할지** (품절/배송불가지역/고객요청대행 등) — 지금 `updateOrderStatus`는 사유 없이 상태만 바뀜
- [ ] 취소 수수료 유무 (일반적으론 배송 전 취소는 무료가 표준)

### 7.2 환불신청(반품)
- [x] **반품 가능 기간** → **법정 최소(단순변심 7일 / 상품하자 30일, 기산점은 인지일) + 판매자가 그 이상 연장 가능**. `return_window_days` 류 필드로 상품/판매자별 저장, 법정 최소 미만 설정은 검증으로 차단
- [x] **사유별 반품배송비 부담 주체** → 업계 표준 채택: 단순변심=구매자 부담, 하자/오배송=판매자 부담. kend-seller 상품등록의 기존 "반품배송비" 필드를 이 용도로 활용
- [x] **판매자 승인 프로세스** → 기간 내 정당한 신청은 원칙적으로 승인해야 하나, 검수에서 객관적 사유(사용/훼손 확인, 기간초과, 법정 제외품목)가 있으면 거절 가능 — "무조건 다 받아줘야 하는 것"은 아님
- [x] **반품 회수 확인 시점과 재고 복원 시점** → 회수확인(검수 승인) 후 복원이 표준 (신청 즉시 복원 시 "실제 미수령인데 재고만 늘어나는" 위험 방지)
- [ ] 반품 사유가 "상품하자"인 경우 회수된 재고를 판매가능재고로 바로 합산할지, 검수대기로 분리할지 — 미정
- [ ] 환불 금액 범위 — 상품가만인지, 배송비(왕복) 포함인지 — 미정
- [x] 무통장입금/가상계좌 관련 → **가상계좌 자체를 통째로 보류**(작업 미착수, 출시 계획에도 없음). 실제로 켤 때 이 항목도 같이 재논의

### 7.3 교환신청
- [x] **구현 방식** → 반품과 별개 트랙(신규 티켓 시스템)이 아니라, **주문목록의 액션**으로 기존 `delivery_items.status`(`exchange_requested`→`exchanged`) 그대로 재사용. 새 테이블 불필요
- [ ] 교환 허용 범위 — 같은 상품의 다른 옵션(사이즈/색상)만 허용할지, 다른 상품으로도 가능한지 — 미정
- [ ] **요청한 옵션 재고가 없을 때** 처리 — 미정 (환불 자동전환 vs 대기)
- [ ] 처리 순서 — 선회수후발송 vs 맞교환(판매자 리스크 큼) — 미정
- [ ] 교환 배송비 부담 주체, 교환 가능 횟수 제한 — 미정

### 7.4 재고관리 (kend-seller 누락 기능)
- [x] **판매자 수동 재고 조정** → kend-seller에서 자체 조사 중 "Stocks Keeping" 메뉴가 기획 초기부터 있었지만 라우트/화면 구현이 없던 죽은 링크였음을 확인. SKU별 재고 조회+수정 화면으로 **Phase 3(관리보완)에 정식 편입**
- [ ] **재고 변경 이력(감사로그) 필요 여부** — 미정. `decrement_stock`/트리거는 단순 증감만 하고 사유 기록이 없어, 재고 불일치 발생 시 원인 추적이 안 됨
- [ ] 재고부족 임계치(현재 10개 고정)를 상품별로 판매자가 설정 가능하게 할지 — 미정
- (참고) 조사 중 **상품 수정 기능 자체가 없음**(재고뿐 아니라 이름/가격 등 전체)도 함께 확인 — Phase 3(관리보완)에 편입

### 7.5 구매확정과의 상호작용
- [ ] 자동 구매확정 기간(배송완료 후 N일) — 정확한 일수 미정, Phase 2.5 착수 시 결정
- [x] **구매확정 이후 하자반품 허용 여부** → 반품 채널을 계속 열어두는 게 아니라, **구매확정 후엔 반품/교환 버튼이 사라지고 "문의하기"(AS/보증 트랙)로만 접수**하는 것으로 결정. 처리 로직(Toss 부분환불·재고) 자체는 반품 채널과 공유
- [x] **구매확정 = 정산 트리거** → 확정. 로드맵상 Phase 2.5(P2.5-2 구매확정) 완료가 Phase 3.5(정산) 착수의 선행조건으로 반영됨

## 9. 업계 표준(쿠팡류 멀티셀러 마켓플레이스) 대비 갭 분석

> 2026-07-28, 팀 회의에서 정리한 `order-flow-policy.md`(업계 표준 참고자료)를 실제 kend
> 코드/스키마와 대조한 결과. ⚠️ 이 자료의 §6(반품 사유 모호성)은 "중고" 특성을 전제로
> 쓰여 있어 kend(신상품)에 그대로 적용할지 확인 필요 — 확인 후 이 문단 갱신.

### 9.1 데이터 모델 — 구조는 사실상 동일, 용어만 다름
| 참고자료 용어 | kend 구현 | 비고 |
|---|---|---|
| 결제(Payment) | `order_groups` | payment_key도 order_groups에 스냅샷 |
| 주문(Order, Payment와 1:1) | *(별도 테이블 없음, order_groups가 겸함)* | 참고자료도 Order=Payment 1:1이라 실질적으로 중복 개념 — 문제 없음 |
| 배송그룹(ShipmentGroup, 판매자 단위) | `orders` | 이름만 다르고 역할 동일 |
| 주문상품(OrderItem) | `order_items` | 동일 |
| 재고: unique item(1개=1행) 권장 | **수량 카운터**(`product_stock_keepings.stock`) | **의도적 차이** — kend는 사이즈별 재고 다건 판매라 카운터 방식이 맞음. 참고자료의 unique-item 권장은 1점만 있는 상품(중고/티켓 등) 기준이라 kend엔 안 맞음 |
| **`shipping_fee_bearer: SELLER \| PLATFORM`** | **없음** | 🔴 **진짜 누락**. 지금 `shipping_fee_type`(FREE/PAID/COD/CONDITIONAL)만 있고 "누가 그 배송비를 부담하는가"를 기록할 컬럼이 아예 없음. 조건부무료/프로모션 배송비를 판매자·플랫폼 중 누가 흡수했는지 나중에 정산할 방법이 없다는 뜻 |

### 9.2 주문(재고 hold) — 이미 표준과 정확히 일치
- ✅ **"결제 성공 후가 아니라 결제 시도 시점부터 재고 hold"** — 코드로 확인함: `product-purchase-modal.tsx:162` 주석에 "주문 결과 처리 → 서버 응답 후 requestPayment() 호출"이라고 명시돼 있고, 실제로 `createOrder`(재고차감 포함)가 Toss 위젯 호출보다 먼저 실행됨. 참고자료가 권장하는 패턴과 정확히 같음 — 우연이 아니라 P2-4 때 B안으로 이미 이렇게 설계했었음
- ⚠️ **hold 유지시간 숫자가 다름**: 참고자료는 "10~15분 후 미결제 시 자동 복원"을 권장하는데, 우리가 만든 `expire_pending_orders`는 **30분**. 재고가 그만큼 더 오래 묶인다는 뜻 — 재검토 여지 있음 (아래 §10에서 이어서 논의)
- ❌ **가상계좌 hold 기간 분리 없음**: 참고자료는 "가상계좌는 입금 대기가 기니까 hold 기간을 별도로 길게(예: 24시간) 가져가야 한다"고 명시. kend는 `virtual_account`가 enum에 정의만 있고 아직 실사용 안 하지만(`PAYMENT_COMING_SOON`), `expire_pending_orders`는 결제수단 구분 없이 일괄 30분 — 나중에 가상계좌 켜면 반드시 손봐야 함
- ❌ **무료배송 조건 재계산 트리거 없음**: 부분취소로 무료배송 기준 밑으로 떨어질 때 배송비를 다시 부과할지의 로직 자체가 없음 (부분취소가 아직 없으니 당연하지만, 만들 때 반드시 포함해야 할 항목으로 §7에 추가 필요)

### 9.3 결제 — 이미 아는 내용과 대부분 겹침
- 금액 서버 재검증, idempotency, 웹훅 폴백 → 전부 `toss-payments.md`의 "라이브 전환 시 처리해야 할 사항" #3/#5/#8과 동일한 항목. **새로운 갭 아님, 기존에 이미 추적 중**
- 승인취소(Void) vs 매출취소(Refund) 구분 → Toss 같은 주요 PG는 취소 API 하나로 내부적으로 알아서 분기해주는 경우가 많아 우리가 직접 구현할 부담은 적음. 다만 **"환불 완료까지 며칠 걸리는지 케이스마다 다르다"는 점을 CS 안내 문구에 반영해야 함** — 지금 어디에도 이런 안내 문구 없음 (사소하지만 놓치기 쉬운 부분)

### 9.4 승인(Acceptance) — 새로 발견된 갭
- ❌ **판매자 미응답 SLA 없음**: 참고자료는 "주문확인 기한(예: 3일) 초과 시 자동취소 + 판매자 페널티"를 권장. kend-seller의 `updateOrderStatus`는 판매자가 언제까지 `confirmed`로 바꿔야 한다는 제약이 전혀 없어서, **판매자가 방치하면 주문이 `pending`에 무기한 머무를 수 있음.** 이건 이번에 새로 찾은, 꽤 실질적인 갭

### 9.5 배송 — 원칙은 일치, 예외 처리가 전부 없음
- ✅ 출고 전 취소 가능/출고 후 불가 원칙은 `SHIPPED_ORDER_STATUSES` 체크로 이미 일치
- ❌ 배송 지연 SLA, 오배송/파손/분실 클레임, 장기 미수령 반송(RTS) 처리 — **전부 미구현.** 다만 이건 이미 §4/§5(환불신청 자체가 없음)에서 알고 있던 큰 구멍의 하위 항목들이라 새 발견은 아님

### 9.6 구매확정 — 애매했던 질문에 대한 답을 하나 얻음
- 이전 §7.5에서 "구매확정 후에도 하자반품 허용해야 하는가"를 열린 질문으로 남겨뒀는데, 참고자료는 **업계 표준 답을 제시**: "구매확정 후 반품/교환(청약철회)은 원칙적으로 불가, 하자는 반품이 아니라 **별도의 AS/보증 청구 트랙**으로 분리". 즉 "구매확정 후 반품 채널을 계속 열어둘지"가 아니라 애초에 **반품 채널과 AS 채널을 처음부터 다른 창구로 설계**하는 게 표준. §7.5 갱신 필요

### 9.7 용어 재정리 — "환불"은 별도 카테고리가 아니라 결제측 결과
기존 문서(§1)는 주문취소/환불신청/교환신청을 나란한 3개 행위로 다뤘는데, 참고자료를 보니 더 정확한 구분은:
- **취소/반품/교환** = **상품(재고) 쪽**에서 일어나는 일 (무엇을 어떻게 되돌리는가)
- **환불** = 그 결과로 **결제(돈) 쪽**에서 일어나는 정산 방식 (Void냐 Refund냐, 카드냐 계좌이체냐)

즉 "환불신청"이라는 사용자 행위는 사실 "반품 신청"이고, 반품이 승인되면 그 정산 방법이 "환불"인 것 — 나란한 카테고리가 아니라 **반품/취소에 딸려오는 하위 결과**.

**(2026-08-04 최종 결정, 아래 §9.7-보완 참고)**: 위에서 "교환을 반품 트랙 하나로 합치는 재설계"를 검토해봤지만, 실제로는 **재설계가 필요 없다** — 지금 스키마(`return_requested`/`returned`/`exchange_requested`/`exchanged`가 처음부터 별도 평행 트랙)를 그대로 쓰면 된다. 대신 훨씬 중요했던 결정은 **"반품/교환 자체가 문의(Q&A) 시스템과 다르다"**는 것이었다 — 아래 참고.

### 9.7-보완 (2026-08-04) — 반품/교환은 "액션", 문의하기는 "Q&A"

논의 중 반품/교환 처리를 "문의 티켓 시스템"으로 통합하는 안을 검토했으나, 최종적으로 기각했다. 이유:
- **반품/교환은 주문 상태를 바꾸는 구조화된 액션**이다 — 지금 이미 동작 중인 "주문취소"(주문목록 버튼 → `orders.status` 전이)와 같은 패턴. 상품 선택 + 정해진 사유 선택 + 제출이라는 **구조화된 폼**이 맞고, 자유 텍스트 문의로 뭉뚱그리면 안 된다
- **"문의하기"는 카테고리별 Q&A**(배송/상품/기타, 구매확정 후 AS 포함)로, 상태전이가 없는 대화형 시스템 — 반품/교환과는 완전히 다른 진입점(버튼 vs 메뉴)이 맞다
- 다만 **뒷단(백엔드) 처리 로직은 상당 부분 공유**한다 — Toss 부분환불 호출, 재고 복원/재출고는 반품 채널이든 AS(문의) 채널을 통해서든 결국 같은 처리 함수를 탄다
- CS관리(구 P2-10)도 "문의하기"라는 하나의 시스템 위에 얹는 **운영 레이어**(필터링/통계/담당자배정)로 정리 — 별도 시스템 아님

이 결정에 따라 새 테이블/티켓 시스템은 "문의하기"용으로만 하나 필요하고(가벼운 Q&A 구조), 반품/교환은 기존 스키마를 그대로 재사용한다. 로드맵 반영: [order-lifecycle-master-plan.md](order-lifecycle-master-plan.md) §1-B.
