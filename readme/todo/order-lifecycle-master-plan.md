## 1. 큰 개념 3개로 구분

### A. 핵심 라이프사이클 (순서대로 한 방향으로 진행)

```
주문생성(재고hold) → 결제 → 판매자확인 → 발송 → 배송중 → 배송완료 → 구매확정
     [15분 SLA]         [3일 SLA]    [N일 SLA]              [자동/수동]
```

각 화살표마다 "이 시간 안에 안 넘어가면 어떻게 되는가"(SLA + 자동화)가 걸려있다.

### B. 정상 흐름을 벗어나는 개입 — "액션"과 "문의"는 서로 다른 것이다

**취소/반품/교환은 질문이 아니라 주문 상태를 바꾸는 액션이다.** 지금 이미 동작 중인
"주문취소"(주문목록 버튼 → `orders.status` 전이)와 같은 패턴으로, 반품/교환도
**이미 스키마에 준비된 `delivery_items.status`**(`return_requested`→`returned`,
`exchange_requested`→`exchanged`)를 그대로 재사용한다. 새 테이블/티켓 불필요.

**"문의하기"는 완전히 별개의 Q&A 시스템이다.** 상태 전이가 없는 대화형 문의(배송/상품/기타,
구매확정 후 AS 포함)를 받는 창구. 주문에 연결될 수도, 안 될 수도 있다.

| 개입 | 성격 | 처리 위치 |
|---|---|---|
| 주문취소 | 주문 상태 액션 (기존 구현) | 주문목록 버튼 |
| 반품/교환 | 주문 상태 액션 (신규, 기존 enum 재사용) | 주문목록 → 단계별 처리는 상세화면 |
| 문의하기 (AS 포함) | Q&A, 상태전이 없음 | 별도 "문의하기" 진입점 |
| 배송 예외 (오배송/파손/분실, RTS) | 반품 사유코드로 흡수 / 배송상태 확장 | 반품 플로우 + sync-tracking |

구매확정 전(청약철회기간 내)엔 반품/교환 버튼이 뜨고, **구매확정 후엔 이 버튼이 사라지고
"문의하기"(AS)로만 접수된다** — 채널이 바뀌는 것이지 처리 로직 자체는 상당 부분 공유한다
(Toss 부분환불·재고 처리는 두 채널 다 동일한 백엔드를 탄다).

### C. 전체를 가로지르는 인프라/정책

- **재고**: hold/차감/복원 ✅ 완료(P2-4), hold 15분 단축 ✅ 완료
- **배송비**: 판매자별 조건부 무료배송 ✅ 기존 구현 + 플랫폼 레벨 조건부 무료배송(신규, 임계값 0=off로 시작) + `shipping_fee_bearer`(누가 부담했는지, 정산 입력값)
- **SLA 자동화**: 결제이탈 ✅ 완료 / 판매자확인(3일) · 발송(일수 미정) — 전부 같은 cron 패턴
- **환불/결제**: Toss 부분취소 연동 (미착수 — 완성되면 "판매자 취소해도 환불 안 되던" 기존 버그도 같이 해결됨)
- **권한**: seller와 administrator가 같은 처리 액션에 접근 — kend-seller에 이미 `role: administrator` 구조 있음 (플랫폼 조건부 배송비 설정도 여기에 추가)

## 3. 작업 순서 (의존성 기준, Phase 2.5 내부)

### Group 1 — 지금 바로 시작 가능 (서로 독립적, 병렬 진행 OK)

| 작업 | 담당 | 비고 |
|---|---|---|
| 1a. 판매자확인 SLA(3일) + 발송 SLA cron | **kend** | `expire_pending_orders` 패턴 재사용 |
| 1b. 플랫폼 조건부 배송비 설정 화면 | **kend-seller (admin)** | `administrator` 전용 메뉴에 추가 |
| 1c. RTS/장기미수령 기간기반 플래깅 | **kend-seller** | `sync-tracking` Edge Function 수정, 미출시 상태라 안전 |
| 1d. 구매확정 로직 (버튼 + 배송완료 후 N일 자동) | **kend** | **Group 3의 필수 선행조건** |

### Group 2 — 스키마 확장 (Group 3 착수 전 필수, kend가 스키마 소유자)

| 작업 | 담당 |
|---|---|
| `delivery_items` 사유(reason) 컬럼 확장 (단순변심/하자/오배송/파손/분실) | **kend** |
| `return_window_days` 류 필드 (판매자가 법정최소 이상 연장) | **kend** |
| `shipping_fee_bearer`(SELLER/PLATFORM) 필드 | **kend** |
| `deliveries.status`에 반송(RTS) 상태 추가 | **kend** |

→ kend가 먼저 해야 kend-seller가 그 위에 화면을 얹을 수 있다 (순차, 병렬 불가).

### Group 3 — 반품/교환/문의 처리 (Group 1의 1d, Group 2 완료 후 착수)

| 작업 | 담당 |
|---|---|
| 반품/교환 신청 UI (주문목록 액션, 구매확정 후엔 숨기고 "문의하기"로 유도) | **kend** |
| 반품/교환 승인·거절 + 검수 처리 화면 | **kend-seller** |
| **Toss 부분환불 연동** (기존 버그 #3도 같이 해결) | **kend** (Toss 시크릿 보유) |
| 반품 승인 시 재고복원 / 교환 시 재출고 | **kend** (기존 트리거 확장) |
| 문의하기 Q&A 코어 (order 선택적 연결, seller+admin 처리) | **kend**(접수 UI) + **kend-seller**(처리 화면, 신규 도메인) |

**정리**: kend = 스키마·크론·구매확정·Toss연동(돈), kend-seller = admin설정·승인화면·RTS·문의처리(운영). Group 1은 바로 병렬 착수 가능, Group 3만 Group 2(스키마) 완료를 기다린다.

## 4. 이거 끝나면 정산(Phase 3.5)만 남는가 — 맞다

Phase 2.5가 끝나면 주문→결제→배송→구매확정의 정상흐름, 그 사이 취소/반품/교환/AS/배송예외까지의 비정상흐름, 재고/배송비/SLA 인프라가 전부 갖춰져 **"구매-재고-배송" 큰 틀이 실질적으로 완결**된다. 남는 건 **Phase 3.5(정산)** 뿐이고, Phase 3(관리보완)은 우선순위 낮은 선택 항목, Phase 4~5는 별개 트랙(QA/디자인/출시)이다.

순서가 필연인 이유: 정산 계산(`P3.5-2`)은 "구매확정된 것만, 취소/환불 제외, `shipping_fee_bearer` 반영"해서 계산해야 하니 Phase 2.5의 산출물이 정산의 입력값이 된다. 이 순서를 어기면 정산부터 만들고 나중에 다시 뜯어고쳐야 했을 것.

## 5. 착수 로그 (2026-08-06~) — 검토했다가 기각한 것들

Phase 2.5 실제 착수하면서 나온 설계 판단 중, **왜 안 하기로 했는지**를 기록해둔다 (나중에 같은 논의를 반복하지 않기 위함).

### 5.1 `confirmed_at` 자동 세팅 — DB 트리거 대신 앱 코드에서 직접 세팅
- **검토했던 안**: 재고 복원 트리거(`handle_order_cancelled`)와 같은 방식으로, `orders.status`가 `confirmed`로 바뀌면 DB 트리거가 자동으로 `confirmed_at`을 채우게 하려 했음
- **기각 이유**: 재고 트리거는 상태를 바꾸는 경로가 실제로 3곳(kend 구매자취소·kend-seller 판매자취소·kend cron)이라 트리거가 필요했지만, `confirmed`로 바꾸는 경로는 **kend-seller의 `updateOrderStatus` 한 곳뿐**이었음. 여러 경로를 걱정할 이유가 없는데 트리거를 쓰는 건 불필요한 복잡도
- **결정**: kend-seller의 `updateOrderStatus`에서 `status`가 `confirmed`로 바뀔 때만 `confirmed_at`도 같이 세팅하도록 직접 구현 (완료, 커밋 `cc382b9`). 이후 발송 SLA cron(`expire_unshipped_orders`)이 이 값을 사용

### 5.2 `product_returns.return_window_days` 필드 — 만들지 않기로 함
- **검토했던 안**: 반품기간(단순변심 7일/하자 30일)을 상품별·판매자별로 설정 가능하게, kend-seller `product_returns` 테이블에 필드 추가 + kend `order_items`에 스냅샷 컬럼 추가
- **기각 이유**: 지금 판매자가 반품기간을 상품별로 다르게(법정 최소보다 길게) 설정하고 싶어할 실제 니즈가 없음. 없는 요구를 위해 스키마+검증+스냅샷까지 미리 만드는 건 과설계
- **결정**: 법정기간을 kend 코드 안에 **상수로 하드코딩** (`CHANGE_OF_MIND`: 7일, 그 외 사유: 30일). `deliveries.delivered_at` + 이 상수로 판정. 나중에 실제로 판매자가 기간 연장을 원하는 사례가 생기면 그때 필드 추가 재논의

## 6. 백로그 (어느 Phase에도 안 넣음 — 할지 말지도 미정)

Phase 2/2.5/3/3.5/4/5 어디에도 배정하지 않은 번외 항목. 착수 시점이 정해지면 그때 적절한 Phase로 옮긴다.

### 6.1 배송조회 상세 이력 화면 (kind: 소비자 UX 개선)
- **현재 상태**: 주문상세 화면(P2.5-2)의 "배송 조회"는 발송/배송완료 시각 + 송장번호만 보여주는 요약형. CJ대한통운 등 택배사 자체 조회 페이지처럼 "상품인수→이동중→배송지도착→배달완료" 단계별 이력(시각·담당점소)은 안 보여줌
- **가능 여부 확인됨**: 스마트택배(SweetTracker) API의 `trackingInfo` 응답에 `trackingDetails` 배열(단계별 `kind`/`time`/`where`/`manName` 등)이 이미 존재 — 기술적으로 가능
- **왜 지금 안 하는가**: kend-seller의 `sync-tracking` Edge Function이 지금 `level`/`complete`만 읽고 `trackingDetails`는 버리고 있음. 이미 실서비스로 도는 함수를 확장해야 해서, 별도로 신중하게 진행하는 게 맞다고 판단해 보류
- **착수 시 방향**: kend-seller가 `sync-tracking`에 `trackingDetails` 저장을 추가(효율성 고려, kend으로 이관하지 않음 — 이유는 §5 유사 사례 참고), kend은 그 데이터를 step-리스트/표로 렌더링
